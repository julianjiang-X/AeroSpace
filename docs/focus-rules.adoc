= Focus rules (local compatibility build)

Some apps focus their own windows: a test host that relaunches, a game, a launcher.
When such a window lives on another workspace, AeroSpace normally follows macOS focus
and switches to that workspace. A focus rule tells AeroSpace to stay where it is.

== Configuration

[source,toml]
----
[[on-window-detected]]
    if.app-name-regex-substring = '^dmhost$'
    run = 'move-node-to-workspace Emu'

[[focus-rules]]
id = 'test-host'
if.app-name-regex-substring = '^dmhost$'
policy = 'ignore-activation'
----

`if` takes the same table keys as `on-window-detected`: `app-id`,
`app-name-regex-substring`, `window-title-regex-substring` and `workspace`.
At least one is required; `during-aerospace-startup` and the command form of `if`
are not accepted. `id` must be unique. The first matching rule wins.
Invalid rules are rejected and the last valid configuration stays loaded.

== Behavior

`ignore-activation`:: When macOS focuses a matching window that is on a workspace
other than the focused one, AeroSpace keeps its focused workspace and window and
gives native focus back to that window. The matching window stays where it is.

The rule applies to every native focus change: an app activating itself, Cmd-Tab,
a Dock click, opening the app again from a launcher. AeroSpace's own commands are
not affected. To reach a matching window, switch to its workspace
(`aerospace workspace Emu`) or use `focus --window-id`; once it is on the focused
workspace, native focus is followed normally.

If the focused workspace has no window, there is nothing to hand focus back to:
the workspace still doesn't change, but keyboard input goes to the matching app
until you focus something else.

An app that re-activates itself continuously is pushed back each time.

`ignore-launch-activation`:: The same, but only while the window's app is launching.
Launching an app (it activates its new window) leaves you where you are; activating it
again afterwards, from a launcher, with Cmd-Tab or from the Dock, takes you to its workspace
as usual, however soon you do it. There is no time window.
Combined with `on-window-detected` moving the window, a launched app lands on its own workspace
in the background:

[source,toml]
----
[[on-window-detected]]
    if.app-id = 'com.example.game-launcher'
    run = 'move-node-to-workspace GAME'

[[focus-rules]]
id = 'game-launch'
if.workspace = 'GAME'
policy = 'ignore-launch-activation'
----

`if.workspace` matches the window's workspace at activation time, after `on-window-detected`
has moved it, so one rule covers every window that lands there.

An app is launching from the moment its process starts until the first native focus change
after it has shown a window:

* it loses native focus after one of its windows held it. AeroSpace handing focus back from
  the ignored activation counts, so the launch normally ends right after that activation.
  If the app activates itself again after that, it is followed;
* or native focus moves to another app's window while the app's window sits unfocused in the
  background (the app launched without activating it).

Consequences:

* Apps that were already running when AeroSpace started are not launching.
* A borderless splash screen doesn't end the launch: AeroSpace treats it as a popup, not as a
  window, so the main window that follows is still the launch activation and is ignored. A splash that is a
  regular window on a matching workspace is the launch activation itself: AeroSpace hands focus
  back, and if the app then activates its main window, that activation is followed.
* If the focused workspace has no window, there is nothing to hand focus back to: the app keeps
  native focus and keyboard input, and its launch ends when you focus something else.
* An app whose window appeared in the background without ever holding native focus is still
  launching until native focus changes. Activating it from another workspace before anything else
  takes focus counts as its launch activation: you stay where you are, and the next activation
  is followed.
